Last week Arpit Bhayani posted [px0](https://px0.ai), a small read-only IDE. It starts in under a millisecond, uses about 20 MB of memory, and opens a repo in the browser with search, symbols, git diffs, and a hand-off to a coding agent when something needs changing. His point was simple: we spend most of our time reading code now, not typing it, and the tools should reflect that.

I tried it and liked it. One problem. I mostly work on virtual machines, and px0 was running on my laptop, looking at the wrong filesystem.

You could already run it on a VM. Bind it to `0.0.0.0`, then reach it over Tailscale or a tunnel. That works, but it is a setup step on every machine, and it puts a server on the network. I wanted something closer to how I already reach those machines, which is ssh.

So I added this:

```bash
px0 ubuntu@vm:~/work/repo
```

It runs px0 on the VM, forwards it back over ssh, and opens my local browser. If px0 is not installed there, it asks and installs it. Ctrl-C stops both ends.

## How it works

There is not much to it. The local px0 picks two ports, one on each side, and runs one ssh command:

```bash
ssh -o ExitOnForwardFailure=yes \
    -L 127.0.0.1:7777:127.0.0.1:41234 \
    ubuntu@vm 'sh -c "<launcher script>"'
```

The remote px0 binds `127.0.0.1:41234`, so nothing is reachable from the VM's network. ssh carries that port to `127.0.0.1:7777` on my laptop, and the browser opens there. Authentication is whatever ssh already does, so keys, agents, config aliases and jump hosts all work without px0 knowing about them.

The launcher script on the remote finds the px0 binary, starts it, and prints its URL. The local side reads that URL from ssh's stdout, swaps the host for the local end of the forward, and opens the browser. Reading stdout is also what makes deep links work: `px0 vm:repo/main.go:42` opens that file at that line, because the remote px0 already puts the path and line in the URL it prints.

## The part that bit me

The thing I cared most about was cleanup. If I close the terminal or the network drops, the px0 on the VM should die. I did not want to leave servers running on machines I forget about.

The trick is to tie the remote process to the ssh session's stdin. The local side holds that stdin open for as long as it runs. When it exits, for any reason, stdin closes on the remote, and a small watcher kills px0:

```sh
"$PX0" -no-open -port 41234 -- "$HOME"/work/repo & p=$!
exec 3<&0
( cat <&3 >/dev/null; kill "$p" 2>/dev/null ) &
wait "$p"
```

My first version did not have the `exec 3<&0` line. It looked right, passed the unit tests, and killed px0 the instant it started. In a non-interactive shell, a background command gets `/dev/null` as its stdin. So `cat` saw end of file immediately and ran `kill`. Duplicating the real stdin onto fd 3 first, and having `cat` read from that, fixes it. px0 is started before the dup, so it holds no copy of the pipe.

I had known this rule about background jobs at some point. I only remembered it by hitting it again. The unit test missed it because the fake ssh in the test printed a banner and waited itself, instead of running the launcher. The fix for that was to make the fake ssh run the real script against a fake px0, which is what the tests do now.

## Installing on the remote

When the launcher does not find px0, it prints one line with `uname -s` and `uname -m` and exits. The local side maps that to a Go platform and asks before doing anything. Then it streams a binary over a second ssh session into `~/.local/bin/px0`.

The rule is that the remote always gets the version I am running. If the platforms match, it is my own executable. If not, it is the release for the remote's platform, downloaded on my side and verified against the release checksums, then streamed over. The remote never needs internet access, and I never have to think about which version is where.

## What I left out

A few things were tempting and did not make it.

Running ssh with a pty would have made the lifetime handling simpler, since the remote gets SIGHUP when the session ends. But it means giving up a clean stdout, and with it the deep links and the check that the remote actually got the port I asked for. Reading stdout was worth the shell script.

I also had a version that re-rendered the remote's output through the local formatting helpers, so the two sides looked identical. It was cosmetic and it was most of the code. Now the output passes through unchanged except for the URL line.

The whole thing is about 400 lines of Go, plus tests. The codebase made that easy. It has a short document listing what the project is and is not, and one of the rules is that px0 never writes to project files itself. That told me which ideas to drop before I started.

## Go, again

This was also the first Go I have written in a long time. It came back fast. `exec.Command`, `bufio.Scanner` over a pipe, a context for shutdown, and not much else. The only bug worth writing about was in the shell, not the Go, which is roughly what I would have predicted.

The branch is [here](https://github.com/divyanshugit/px0/tree/feat/port-forward). If you read more code than you write, and that code lives on machines you ssh into, try px0.
